# 用户故事质量检查与拆分方法

在 SKILL.md 第 3 步拆分故事前阅读本文件。

## INVEST 检查清单

每个故事写完后，逐条检查：

| 字母 | 标准 | 自检问题 | 不满足时怎么办 |
|---|---|---|---|
| **I** | Independent 独立 | 能不能单独开发、单独上线？ | 合并强耦合的故事，或把共同依赖抽成 Enabler |
| **N** | Negotiable 可协商 | 写的是"要解决什么"，还是"必须这样实现"？ | 删掉具体的实现细节（如"用下拉框"），保留目标 |
| **V** | Valuable 有价值 | "以便"那一句，用户或业务真的在乎吗？ | 写不出价值，就移入待确认问题 |
| **E** | Estimable 可估算 | 开发看完能大致判断工作量吗？ | 信息不足的部分列入待确认问题 |
| **S** | Small 足够小 | 能在一个迭代（通常 1–2 周）内完成吗？ | 按下文的方法拆分 |
| **T** | Testable 可测试 | 验收标准能明确判断"通过 / 不通过"吗？ | 把模糊描述改成可观察的结果 |

## 常用拆分方法

故事太大时，按以下方法拆分。优先选择**拆完后每一块都能单独交付价值**的方法。

| 方法 | 说明 | 示例 |
|---|---|---|
| 按工作流步骤 | 一个长流程拆成多个步骤 | "在线预约" → 选科室 / 选时段 / 确认提交 |
| 按业务规则 | 先做最简单的规则，复杂规则后补 | 先支持"取消预约"，再支持"24 小时内取消需扣费" |
| 按正常 / 异常路径 | 先做正常路径，异常处理单独成故事 | 先做"上传成功"，再做"上传失败重试" |
| 按数据类型 | 不同类型的输入分开处理 | 先支持 PDF 导入，再支持图片 OCR |
| 按用户角色 | 不同角色的需求分开 | 先做患者端，再做医生端 |
| 按操作类型 | 增、查、改、删分开 | 先做"查看报告"，再做"分享报告" |
| 先简单后完善 | 先手动或半自动，再全自动 | 先人工审核，再接入 AI 自动审核 |

## 不要这样拆

- **按技术层拆**：拆成"前端页面""后端接口""数据库表"三个故事。单独哪一个都不能给用户带来价值，应该作为一个故事的子任务，而不是三个故事。
- **拆得过细**：拆到"添加一个按钮"这种粒度，管理成本会超过收益。一般一个故事对应用户能感知到的一个完整小目标。

## 验收标准常见问题

| 问题写法 | 为什么不好 | 改进写法 |
|---|---|---|
| 页面加载要快 | 无法判断是否通过 | Then 首屏在 2 秒内显示（4G 网络） |
| 界面简洁友好 | 主观描述 | Then 完成预约的点击次数不超过 4 次 |
| 支持各种异常情况 | 范围不明确 | Given 网络断开，When 点击提交，Then 提示"网络异常，请重试"并保留已填写内容 |
| AI 回答要准确 | 无法测试 | Then 回答附带来源引用；Given 知识库中无相关内容，Then 回复"暂无相关信息"而不是编造答案 |
