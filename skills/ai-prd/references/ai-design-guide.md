## 1. 技术方案选择

PM 不需要决定实现细节，但需要说清楚**为什么选这个方案、代价是什么**。

| 方案 | 适合 | 不适合 | 主要代价 |
|---|---|---|---|
| **提示词工程** | 通用任务：摘要、改写、分类、简单问答 | 需要私有知识或最新信息 | 效果上限受模型本身限制 |
| **RAG（检索增强生成）** | 基于私有文档、知识库回答问题；需要引用来源 | 需要改变模型的说话风格或推理方式 | 需要维护知识库；检索不准会导致回答错误 |
| **微调** | 固定格式输出、特定风格、领域术语多；有大量高质量标注数据 | 知识经常更新；数据少 | 需要标注数据和训练成本；模型更新后要重新训练 |
| **Agent（智能体）** | 需要多步操作、调用工具或外部系统 | 单步就能完成的任务 | 延迟和成本高；出错路径多，更需要人工确认 |

**选择顺序建议**：先试提示词工程 → 需要私有知识再加 RAG → 效果仍不够且有数据时再考虑微调。Agent 只在确实需要多步操作时使用。PRD 中应说明为什么不选更简单的方案。

**模型选择的考虑因素**：

| 因素 | 要回答的问题 |
|---|---|
| 效果 | 在本功能的评测集上表现如何？ |
| 成本 | 按预计调用量，每月成本是多少？ |
| 延迟 | 用户能接受等多久？是否需要流式输出？ |
| 部署方式 | 能否调用外部 API，还是必须私有化部署？ |
| 合规 | 数据能否发送给模型提供方？提供方是否会用数据训练？ |
| 语言 | 对中文或目标语言的支持如何？ |

## 2. 评测计划

### 离线评测集

上线前用来判断"够不够好"。构建要点：

- **来源**：优先用真实数据（历史工单、真实用户问题），其次是人工编写。不要只用 AI 生成的问题，它们往往比真实问题更规整
- **覆盖面**：至少包含以下几类
  - 高频的典型问题
  - 难例：表述模糊、有错别字、口语化、多个问题混在一起
  - **应该拒答的问题**：知识库里没有答案的、超出功能范围的、有风险的
  - 边界情况：超长输入、空输入、其他语言
- **规模**：早期 50–100 条即可起步，覆盖面比数量更重要。PRD 中写明计划规模，以及随上线逐步扩充
- **标注**：每条写明期望答案或判断标准，由谁标注，如何保证一致性（如两人独立标注后对比）

### 常用指标

按功能类型选择，不需要全部使用：

| 功能类型 | 指标 | 说明 |
|---|---|---|
| 问答 / RAG | 回答准确率 | 人工或规则判断回答是否正确 |
| | 引用准确率 | 引用的来源是否真的支持该回答 |
| | 拒答准确率 | 该拒答的问题是否正确拒答 |
| | 检索命中率（Hit@K） | 正确文档是否出现在前 K 条检索结果中 |
| 分类 / 判断 | 精确率、召回率 | 根据误判和漏判哪个代价更大，确定重点看哪个 |
| 生成 / 写作 | 人工评分（1–5 分） | 制定评分标准，多人评分取平均 |
| | 格式符合率 | 输出是否符合要求的格式 |
| Agent | 任务完成率 | 端到端完成任务的比例 |
| | 越权操作次数 | 应为 0 |
| 通用 | 响应时间（P50 / P95） | |
| | 单次成本 | |

**写明取舍**：例如反欺诈场景"宁可多拦截也不能漏"，重点看召回率；推荐场景"宁可少推也不能推错"，重点看精确率。把这个取舍用业务语言写出来，比只写数字更重要。

### 在线评测

上线后持续监控：

- **用户反馈**：点赞 / 点踩、"这个回答有帮助吗"、用户修改 AI 输出的比例
- **行为指标**：采纳率、重新生成率、转人工率、使用后的任务完成率
- **Bad Case 收集**：定期抽样差评和转人工的案例，补充到离线评测集

### 上线门槛（Go / No-Go）

为每个关键指标设定阈值，例如：

| 指标 | 门槛 | 说明 |
|---|---|---|
| 回答准确率 | ≥ 85% | 建议值，需团队确认 |
| 拒答准确率 | ≥ 95% | 宁可不答也不能乱答 |
| 高风险错误 | 0 条 | 评测集中出现任何一条即不上线 |

至少设置一条"**一票否决**"的指标，对应最不能接受的失败。

## 3. 失败模式与兜底

用下表逐条列出：

| 失败模式 | 示例 | 严重程度 | 如何发现 | 兜底方案 |
|---|---|---|---|---|

常见失败模式：

| 失败模式 | 常见兜底方案 |
|---|---|
| **幻觉**：编造不存在的信息 | 使用 RAG 并要求引用来源；无依据时拒答；展示来源让用户核实 |
| **答非所问** | 意图识别；不确定时向用户澄清 |
| **越界回答**：回答了超出范围的问题（如医疗诊断、法律意见） | 范围限定提示词；关键词和意图拦截；固定话术 + 转人工 |
| **有害或不当内容** | 输入输出内容审核 |
| **提示词注入**：用户或文档中的内容诱导 AI 违反规则 | 区分系统指令和用户内容；高风险操作需确认 |
| **过时信息** | 知识库定期更新；展示信息日期 |
| **服务不可用或超时** | 降级为非 AI 方案（如普通搜索、人工客服），而不是直接报错 |
| **过度依赖**：用户不加核实就采纳 AI 输出 | 界面提示"AI 生成，请核实"；关键场景要求用户确认 |

**严重程度**建议用三级：致命（造成实际伤害或合规问题）/ 严重（用户被误导或任务失败）/ 一般（体验变差）。致命级必须有明确的兜底方案。

## 4. 人工介入分级

按"**出错的后果是否可逆**"和"**影响范围**"判断 AI 能自主到什么程度：

| 级别 | AI 的权限 | 适用 | 示例 |
|---|---|---|---|
| L1 自动执行 | AI 直接执行，事后可查看 | 只读、可逆、影响小 | 生成摘要、搜索、草稿 |
| L2 用户确认 | AI 提出建议，用户确认后执行 | 会改变数据或状态，但可撤销 | 修改文件、发送前的邮件、填写表单 |
| L3 人工处理 | AI 只做辅助，最终由专业人员决定 | 不可逆、高风险、涉及专业判断 | 医疗建议、理赔拒付、删除数据、对外付款 |

PRD 中应列出功能涉及的每类动作，并标明级别。

确认环节的设计要点：

- 确认界面要显示**AI 要做什么、作用在哪里、风险是什么**，让用户能在几秒内判断
- 避免确认过于频繁，否则用户会不看就点确认。低风险的同类操作可以提供"本次会话内始终允许"
- 用户离开时（如手机切到后台），需要确认的操作应暂停等待，而不是自动执行

## 5. 数据与合规

PM 需要识别**需要满足什么要求**，具体判断交给法务和合规团队。逐项检查：

| 检查项 | 要回答的问题 |
|---|---|
| 数据类型 | 是否涉及个人信息？是否涉及敏感个人信息（健康、金融、生物识别、未成年人等）？ |
| 用户授权 | 是否需要用户单独同意？授权说明是否用普通人能看懂的语言？ |
| 最小必要 | 发给模型的数据是否只包含完成任务所必需的部分？能否先脱敏？ |
| 数据流向 | 数据发给哪个模型提供方？是否出境？ |
| 训练使用 | 用户数据是否会被用于训练模型？用户能否选择退出？ |
| 存储与删除 | 对话和输出保存多久？用户能否删除？ |
| 访问控制 | 谁能看到用户的对话记录？是否有审计日志？ |
| 行业与地区规定 | 所在行业和地区对 AI 和数据有什么特别规定？（需法务确认） |
| AI 标识 | 是否需要向用户说明内容由 AI 生成？ |

## 6. 成本与延迟

- **成本估算**：预计日调用量 × 单次平均成本。写明假设（如平均输入和输出长度）
- **延迟预算**：用户能接受的等待时间。超过 2–3 秒的等待，考虑流式输出或显示进度
- **降低成本的手段**：缓存常见问题的答案、简单问题用小模型、限制输入长度。PRD 中写明预算上限即可，具体手段由技术团队决定
